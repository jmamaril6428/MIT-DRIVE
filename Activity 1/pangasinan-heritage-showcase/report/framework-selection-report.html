Decision in one paragraph

I recommend Vue with Nuxt 3 in pre-rendered static-site mode for this information-oriented heritage showcase. Both permitted options can deliver static HTML, but the weighted project assessment narrowly favours Nuxt (84/100 versus 81/100). A measured historical runtime proxy favours Vue; it does not establish a whole-application performance advantage. The recommendation is conditional on the same-fixture production-build test described below. [1] [2]

Scope: this report and the companion Atomic Design library answer the two deliverables in the uploaded two-page “2026 Activity 1.pdf.” The attachment does not include separate final-exam questions. 1. Problem definition and architecture

The brief positions the learner as an architect for a provincial tourism initiative. The platform must present Hundred Islands, Cape Bolinao Lighthouse, and Balungao Hot Springs in a resilient, mobile-first, accessible way. The “60%+ mobile” figure is a scenario assumption supplied by the instructor, not a statistic independently established in this report.

My MIT perspective is that the framework is only one part of the solution. A small download is valuable, but maintainability, content governance, accessibility, and deployability must be designed together. “Instant” loading cannot be guaranteed on every 3G connection.

Proposed JAMstack content flow

Versioned JSON/Markdown content → validated build input → Nuxt pre-rendering → static HTML/CSS/JS and pre-sized image files → GitHub Pages → visitor browser. Nuxt supports pre-rendering for static hosts; GitHub Pages serves static repository assets. [1] [3]

Store title, slug, municipality, summary, image alt text, source URL and last-reviewed date independently from components. A tourism editor changes content through a pull request; the reviewed merge triggers a rebuild. The browser does not need CMS credentials or a CMS request before the page becomes readable. A headless CMS could later replace the file source, but that service and any fees are outside the current zero-cost static-hosting proposal.

Arithmetic: (47,056 − 33,841) / 47,056 × 100 = 28.08% less compressed data for this Vue runtime fixture. At an assumed effective transfer rate of 125,000 bytes/s, the 13,215-byte difference is approximately 0.106 seconds of payload transfer, excluding latency, parsing and other assets.

Limitation: these are different library distribution formats and separately compressed files. Neither includes a framework router, route payload, hydration overhead, application code or images. ESM tree shaking and React Server Component boundaries can change the result. Therefore these values must not be quoted as “Nuxt is 28% faster than Next.js.” The evidence supports a provisional payload preference only.

4. Deployment, performance and risk controls

4.1 GitHub Pages deployment plan

For the proposed Nuxt application, keep server rendering enabled during generation and pre-render every destination. For a project repository named pangasinan-heritage, set the base path to /pangasinan-heritage/. For a user-site root, use /. Upload only .output/public/ to Pages; do not upload a Node server output. [1] [3]

// Nuxt 3 integration example
export default defineNuxtConfig({
  ssr: true,
  app: { baseURL: process.env.NUXT_APP_BASE_URL || '/' },
  nitro: { prerender: { routes: [
    '/', '/sites/hundred-islands',
    '/sites/cape-bolinao', '/sites/balungao'
  ] } }
})
# After creating a real Nuxt project and locking dependencies:
NUXT_APP_BASE_URL=/pangasinan-heritage/ npm run generate

The included .github/workflows/pages.yml instead publishes the supplied component library from template/. This is a working static-library handoff, not a claim that Nuxt was built. The student must upload the repository, enable Pages under “GitHub Actions,” and verify the actual deployment.

4.3 Risks and mitigations

  • Historical major versions: the instructor specifies Next 14/Nuxt 3. Before a public release, verify support and advisories, choose patched dependencies, and obtain instructor approval if a major-version change is necessary.
  • No server on Pages: do not put secrets, bookings, private records, authentication endpoints or runtime CMS credentials in static files.
  • Stale tourism facts: use source URLs and review dates; confirm fees, hours, advisories and accessibility facilities with local authorities.
  • Accessibility: component contrast and keyboard tests support the goal, but a framework or automated score alone cannot establish WCAG 2.1 AA conformance. [4]
  • Images: current examples use third-party photographs for educational preview. Clear usage rights and produce responsive derivatives before public tourism publication.

5. Verification protocol and conclusion

Fair full-framework benchmark to run before release

  1. Pin exact Next.js 14, React, Nuxt 3, Vue and Node versions. Record lockfiles, OS and hardware. Use the same text, three sites, image derivatives, routes and interaction features.
  2. Build production static outputs with next build (output:'export') and nuxt generate. Serve those outputs over the same host. [2] [1]
  3. Record cold first-route transfer from a HAR: HTML, CSS, loaded JS, route payload and images separately. Do not sum every file in an output directory as the initial download.
  4. Use the same fixed mobile viewport, throttling profile and cache settings. Run five cold loads per candidate; compare median LCP, total bytes, request count and layout shift. Keep raw reports.
  5. Run a timed developer pilot: add one destination and one accessible card variant in each stack; record actual minutes, defects and review effort. No such times are claimed in this report.
  6. Run automated accessibility checks and manual keyboard, focus, zoom, reflow and screen-reader tests. Update the decision matrix if evidence changes the ranking.

Conclusion

Nuxt 3 is my selected framework for this static, content-first tourism scenario. Its recommendation is a reasoned architectural judgement with quantitative support and explicitly bounded evidence, not a universal ranking. The strongest design choices are pre-rendered content, limited JavaScript, optimized imagery, reusable components and a verifiable accessibility process. The companion manual turns those principles into a ten-component library that another developer can inspect and extend.
